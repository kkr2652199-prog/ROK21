## 2) STEP 2 — 원인 규명

### 스케줄러 경로

`app/lotto/draw_scheduler.py` → `_job_collect_latest()` → **`app.lotto.data_service.collect_latest_forward`**  
→ `save_draw_full` / `get_lotto_db()` = **`data/lotto4.db`만**.  
수집 후 `lotto4.all_combos_service.sync_winner_for_draw`만 추가 호출.  
**testlotto·hyodo 호출 없음.**

### K-06 = 직접 원인인가?

**예.** per-draw fan-out 미구현이 이번 hyodo 후미 갭의 **직접 원인**이다.  
스케줄/자동 수집이 lotto4만 갱신하고, hyodo는 별도 수동 `POST /hyodo/fetch-latest` (`app.hyodo.data_service.fetch_latest_draw` → 자체 API 수집)에 의존한다.

### hyodo = 별도 수집 vs 팬아웃 누락?

| 판정 | 근거 |
|------|------|
| **자체 수집 경로 존재** | `app/hyodo/data_service.py` `fetch_single_draw` / `save_draw` → `lotto_hyodo.db` |
| **이번 갭의 성격** | 팬아웃 누락 + hyodo 수동 fetch 미실행 → **후미 3회 미적재** |
| testlotto | 동일 구조이나 K-07에서 이미 1234까지 복구됨 |

**결론:** hyodo는 “별도 DB·별도 fetch API”이지만, 주간 자동 경로에서는 **팬아웃 대상에서 누락**된 것이 갭의 운영 원인이다.

## 5) STEP 5 — 팬아웃 영구화 안 (코드 작성 금지)

### 목표

다음 회차부터 lotto4 수집 성공 시 testlotto·hyodo `lotto_draws`에 **동일 회차 INSERT OR IGNORE**가 자동 반영되어 trailing 갭이 재발하지 않게 한다.

### 최소 변경안 (설계만)

1. **훅 위치:** `app/lotto/draw_scheduler.py`의 `_job_collect_latest` 안, `collect_latest_forward`가 `collected` 리스트를 반환한 직후.  
   (또는 `collect_latest_forward` 말단 — 스케줄·수동 공통이면 data_service 쪽이 낫다.)
2. **동작:** 각 `draw_no ∈ collected`에 대해 lotto4에서 행 SELECT →  
   `app.testlotto.data_service.save_draw` / `app.hyodo.data_service.save_draw` 호출  
   (이미 `INSERT OR IGNORE`이므로 멱등).
3. **금지:** 대상 DB 기존 행 UPDATE · 외부 재크롤(소스=lotto4 행) · 예측/review 자동 재생성은 **별 승인**(이번 정합 범위 밖).
4. **실패 정책:** 팬아웃 실패는 warning 로그 + 결과에 `fanout_errors` 배열. lotto4 수집 성공은 롤백하지 않음.
5. **검증:** 스케줄 dry-run 또는 단위 테스트로 “lotto4만 +1 → 3DB MAX 동반 +1” assert.
6. **K-06:** 위 구현 시 PATCHED 후보. **본 턴은 안만 · 구현 0.**

### 대안 (비권고)

- testlotto/hyodo 각자 cron fetch: 외부 API 의존·불일치 위험.  
- DB 파일 공유: 앱 경계·락·스키마 진화에 취약.
